# Kubernetes Scheduling & Autoscaling — Requests, Limits, HPA, VPA & Karpenter

## 1. Why Should I Care About This?
- **You Are Almost Certainly Paying For 4× The Cluster You Use**: CAST AI's Kubernetes Cost Benchmark, computed across thousands of real clusters, has repeatedly found average CPU utilisation around **10%** and memory around **20–23%** of what was provisioned. Datadog's Container Report finds roughly **half of all containers using less than a third of the CPU and memory they request**. That gap is not waste from bad code — it is the direct arithmetic consequence of `resources.requests`, and it is the single largest line item in most Kubernetes bills.
- **The Latency Bug That Isn't A Latency Bug**: A service with `limits.cpu: 1` and four worker threads exhausts its 100 ms CFS quota in **25 ms** and is then *frozen for 75 ms*. Average CPU reads a perfectly healthy 1.00 core while p99 latency gains 75 ms per period. Engineers chase GC, the database, and the network for weeks. The answer is one counter: `container_cpu_cfs_throttled_seconds_total`. The Linux kernel even had a genuine CFS accounting bug making this worse, fixed in **kernel 5.4** (commit `de53fd7aedb1`, contributed after production throttling investigations at Indeed).
- **Exit Code 137 Is Not Negotiable**: CPU over its limit gets throttled; memory over its limit gets `SIGKILL`ed by the kernel OOM killer with no grace period, no `preStop` hook, and no chance to flush. The pod restarts into `CrashLoopBackOff` with backoff doubling to a 5-minute cap. **CPU is compressible and memory is not** — that asymmetry decides how you set every limit you will ever set.
- **"It Autoscales" Is Four Different Statements**: HPA changes pod *count*, VPA changes pod *size*, Cluster Autoscaler/Karpenter change node *count*, KEDA scales on *events* and down to zero. They run independently, on different clocks (15 s vs minutes vs ~3 minutes), and two of them will actively fight each other on the same workload. Naming which one you mean is the first thing a senior interviewer listens for.

## 2. What Problem Does This Solve?
- **Bin-Packing Without Knowing The Future**: A cluster is a bin-packing problem where item sizes are unknown at pack time. Requests are the declared size — the scheduler's only input. Get them wrong and you either strand capacity (requests too high) or oversubscribe into node-level thrashing (requests too low).
- **Noisy Neighbours On A Shared Kernel**: Containers share one kernel and one set of cgroup controllers. Without requests, one runaway pod starves every co-tenant on the node; without limits, one memory leak takes the node — and every pod on it — down together.
- **Reacting To Load Without A Human**: Traffic moves on a diurnal 3–5× curve plus unpredictable spikes. Manual capacity means either paying for peak 24/7 or being paged. Autoscaling makes capacity a function of a measured signal — but only if you pick a signal that actually leads demand.
- **Ordering Disruption So It Isn't An Outage**: Node upgrades, spot reclamation, scale-down, and VPA re-sizing all *evict pods*. Without QoS classes, PodDisruptionBudgets, topology spread, and PriorityClasses, "routine maintenance" and "a partial outage" are the same event.
- **Naive Approach**: Copy the requests and limits from another team's YAML (or leave them out entirely), set an HPA on `cpu: 80%`, and call it done. What actually happens: requests are 4× real usage so the cluster reports 95% allocated at 20% utilised and Cluster Autoscaler keeps buying nodes; the CPU limit throttles the app so p99 is bad *and* the HPA's own signal is distorted; the pods that omitted requests land in `BestEffort` and are the first thing evicted during the incident; and nobody set a PDB, so the next node drain takes all three replicas of the same service off at once because they were all bin-packed onto the same node.

## 3. Core Idea (Intuition First)
Think of a node as an **airline seat map, and requests as the reservations**.

- The **request is a reservation**. The scheduler is the booking system: it adds up reservations and refuses to sell seat 8A twice. It has no camera in the cabin — **it never looks at whether anyone is actually sitting there.** A plane can be "sold out" with twenty people on board.
- The **limit is the seatbelt sign**. It has nothing to do with booking; it is enforced *in the cabin, continuously*, by a different authority (the kernel's cgroup controllers). For CPU the enforcement is "sit down for the rest of this 100 ms" — annoying, recoverable. For memory it is "you are ejected at 30,000 feet" — `SIGKILL`, instantly.
- **QoS class is derived, never declared.** Kubernetes reads your requests and limits and assigns `Guaranteed` / `Burstable` / `BestEffort`, and that class decides who gets thrown out first when the node runs short.
- **Autoscaling adds and removes seats and planes.** HPA books more seats (replicas), VPA changes how big each reservation is, Cluster Autoscaler/Karpenter charter another aircraft, and KEDA decides based on the queue at the gate rather than the temperature in the cabin.
- The **overcommit ratio** `Σlimits / Σrequests` is how much you are gambling that not everyone flies at once. It is a deliberate, priced bet — and for memory the correct bet is usually **1.0**.

> The mental image: **a request is a promise you make to the scheduler; a limit is a threat the kernel makes to you.** They share a YAML block and nothing else.

## 4. How It Actually Works

### 1. Requests drive scheduling, limits drive runtime — and they never talk
- **The request is written into `NodeInfo`, not measured.** When kube-scheduler evaluates a node, the `NodeResourcesFit` plugin computes `Σ requests of all non-terminated pods on the node` and compares it to **allocatable**, which is `capacity − kube-reserved − system-reserved − eviction-hard`. On EKS that reservation is roughly `90m` CPU on an 8-vCPU box plus `255 MiB + 11 MiB × maxPods` of memory; GKE reserves 25% of the first 4 GiB, 20% of the next 4 GiB, 10% of the next 8 GiB, and 6% above that. **You do not get the instance you paid for** — budget ~5–10% off the top before any of your pods exist.
- **Actual usage is never consulted.** There is no feedback path from cAdvisor to the scheduler. This is a deliberate design choice: scheduling on live usage would be non-deterministic, would oscillate, and would let a pod that happens to be idle at bind time get scheduled onto a node it will then crush. The cost of that determinism is the utilisation gap.
- **Requests also become cgroup weights.** `requests.cpu: 500m` sets `cpu.shares = 512` (cgroup v1) or `cpu.weight ≈ 20` (v2). This is the *good* half of requests: under contention the kernel divides CPU **in proportion to requests**, so a request alone already protects you from a noisy neighbour, with no throttling and no wasted headroom. `requests.memory` sets no cgroup value at all — it is purely a scheduling number plus an eviction-ranking input.
- **Overcommit ratio** = `Σ limits / Σ requests` on a node. A ratio of 1.0 is no gamble and no density; 3–4× is common for CPU in dev/batch clusters; **for memory the honest ratio is 1.0**, because losing the bet means OOMKills rather than slowness.
- **Trade-off, and when the other choice wins**: requests-based scheduling wastes capacity, and the alternative — usage-aware descheduling — genuinely exists (the [descheduler](https://github.com/kubernetes-sigs/descheduler) has a `LowNodeUtilization` strategy, and Karpenter's consolidation does something similar at the node level). Use them as a *second loop* that rebalances after the fact; never try to make the primary scheduling decision on live usage.

### 2. CPU is compressible: the CFS quota, and why throttling looks like a mystery
- `limits.cpu: 1` writes `cpu.cfs_period_us = 100000` and `cpu.cfs_quota_us = 100000` (cgroup v2: `cpu.max 100000 100000`). Read it as: **"this cgroup may consume 100 ms of CPU time per 100 ms of wall clock."**
- **The mechanism, step by step.** (1) At the start of each 100 ms period the cgroup's quota is refilled. (2) Every runnable thread in the cgroup draws from that one shared bucket, *in parallel* — 4 threads on 4 cores draw 4 ms of quota per 1 ms of wall clock. (3) When the bucket hits zero, the CFS bandwidth controller **dequeues every thread in the cgroup** (`throttle_cfs_rq`) regardless of what they were doing. (4) They stay off the runqueue until the next period boundary. (5) The counters `container_cpu_cfs_throttled_periods_total` and `container_cpu_cfs_throttled_seconds_total` increment.
- **The concrete failure**: a 4-thread JVM or Go service with `limits.cpu: 1` burns its whole quota in **25 ms** and is then **hard-stalled for 75 ms**. A request that arrives at t=30 ms waits 70 ms before its thread is even runnable. Average CPU utilisation reads 1.00 core — *exactly at the limit, looking perfectly healthy* — while p99 latency is destroyed. This is why "high p99, normal average CPU" should immediately make you check throttling.
- **The metric that settles it**: `rate(container_cpu_cfs_throttled_periods_total[5m]) / rate(container_cpu_cfs_periods_total[5m])` is the fraction of periods in which you were stalled. Anything above ~1% on a latency-sensitive service is a real problem; above 25% you are running a different application than you think you are.
- **The genuine industry debate.** A well-argued position (Buffer's engineering write-up on removing CPU limits; Robusta's widely circulated "stop using CPU limits" post; Zalando's production guidance) is: **set CPU requests, do not set CPU limits.** Requests already give you proportional-share protection under contention, and the throttling caused by limits is a self-inflicted latency wound. The counter-argument: without limits a runaway pod can consume all *idle* CPU on a node, hurting co-tenants' tail latency in ways shares don't fully prevent, you lose `Guaranteed` QoS and CPU pinning, and cost attribution gets fuzzy. **The defensible middle**: no CPU limits on latency-sensitive online services, CPU limits on batch and untrusted tenants, and always a CPU *request* that reflects real steady-state usage.
- Also worth knowing: a **kernel bug** in CFS bandwidth control (unused per-CPU slack expiring, so multi-threaded apps were throttled far below their quota) was fixed in **Linux 5.4** and backported. If you see throttling at 30% of quota on an old kernel, check the kernel version before you re-architect anything.

### 3. Memory is not compressible: OOMKill, eviction, and QoS classes
- `limits.memory: 512Mi` writes `memory.max = 536870912`. There is no quota, no period, no throttling. The instant a page allocation would push the cgroup's `memory.current` over the limit and reclaim fails, the **kernel's cgroup-scoped OOM killer** fires: `SIGKILL`, immediately, to the largest-scoring process in the cgroup. No `SIGTERM`, no `terminationGracePeriodSeconds`, no `preStop` hook, no flush of a buffer.
- **What you observe**: `kubectl describe pod` shows `lastState.terminated.reason: OOMKilled` and `exitCode: 137` (128 + signal 9). The container restarts; repeated kills produce `CrashLoopBackOff` with exponential backoff 10 s → 20 s → 40 s, capped at 5 minutes. Alert on `increase(kube_pod_container_status_restarts_total[15m])` joined with the `OOMKilled` reason, not just on restart count.
- **QoS classes are derived from your requests and limits, not declared:**
  - **`Guaranteed`** — every container in the pod sets *both* CPU and memory, and `requests == limits` for both. `oom_score_adj = −997`, evicted last, and (with `--cpu-manager-policy=static` on the kubelet and an **integer** CPU request) eligible for **exclusive core pinning**, which removes CFS throttling entirely and preserves L1/L2 cache locality and NUMA affinity. This is what a latency-critical or CPU-cache-sensitive workload wants.
  - **`Burstable`** — at least one request is set, and it isn't `Guaranteed`. `oom_score_adj = clamp(1000 − 1000 × memRequest/nodeMemory, 2, 999)`, so **a bigger memory request literally buys you a better survival score**. Evicted second, with the pod most over its *own* memory request going first.
  - **`BestEffort`** — no requests and no limits anywhere. `oom_score_adj = 1000`, i.e. the kernel's preferred victim, and the first thing kubelet evicts under `MemoryPressure`. The scheduler also treats it as consuming zero, so it always "fits" — which is exactly why it dies.
- **Node-level eviction is a separate mechanism from the cgroup OOM killer.** kubelet watches node-wide signals against `--eviction-hard` (defaults include `memory.available<100Mi`, `nodefs.available<10%`, `imagefs.available<15%`) and *proactively* evicts pods in QoS order to protect the node, with `SIGTERM` and a grace period. So there are two ways to die by memory: your own cgroup limit (hard kill), or the node running short (graceful eviction, QoS-ordered). Guaranteed pods are safe from the second but not the first.
- **The practical rule this produces**: `requests.memory == limits.memory`, always, for anything you care about. For CPU, `requests` mandatory, `limits` optional and often harmful.

### 4. The scheduler, mechanically: filter → score → bind
- kube-scheduler runs a loop pulling one pod at a time off a priority queue, and each pod goes through a plugin framework with two decisive phases:
- **Filter (predicates)** — reduce all nodes to *feasible* nodes. `NodeResourcesFit` (do the requests fit in allocatable?), `NodeAffinity` / `NodeUnschedulable`, `TaintToleration`, `PodTopologySpread`, `InterPodAffinity`, `NodePorts` (host-port conflicts), `VolumeBinding` (does a `WaitForFirstConsumer` PV's zone match?), `VolumeZone`, `NodeVolumeLimits` (a `m5.large` can only attach so many EBS volumes). If zero nodes survive, the pod stays `Pending` with `reason: Unschedulable` — **and that event is the only trigger the cluster autoscaler ever sees.**
- **Score (priorities)** — rank the survivors 0–100 each, weighted and summed. `NodeResourcesFit` with the **`LeastAllocated`** strategy spreads load (the default, and the reason a fresh cluster distributes pods rather than filling one node); switch it to **`MostAllocated`** for aggressive bin-packing when you want the autoscaler to be able to empty and delete nodes. `ImageLocality` favours nodes that already have the image cached — worth real seconds on a 2 GB image. `PodTopologySpread` and `InterPodAffinity` add their preferences here.
- **The performance knob**: scoring every node in a 5,000-node cluster is wasteful, so `percentageOfNodesToScore` stops early. The default (`0` = adaptive) computes `max(50 − numNodes/125, 5)` percent — so a 1,000-node cluster scores ~42% of nodes and a 5,000-node cluster scores the floor of 5%. **This trades placement optimality for throughput, and it means the scheduler's answer is "good", not "best".**
- **Bind is optimistic.** The scheduler `assume()`s the pod onto the node — updating its in-memory cache immediately so the next pod sees the node as fuller — and then writes the `Binding` asynchronously. The kubelet on that node runs its *own* **admission** check on the real, current node state, and can reject: you get a pod in `Failed` phase with `reason: OutOfcpu` or `OutOfmemory`. This is a genuine race, not a bug, and it's why you occasionally see failed pods on a node the scheduler was sure had room.
- **Preemption**: if a pod with a high `PriorityClass` can't be scheduled, the `PostFilter` phase looks for a node where evicting lower-priority pods *would* make it fit, picks the victim set that minimises damage (respecting PDBs on a best-effort basis), and deletes them with their grace period. Built-in classes: `system-cluster-critical` (2000000000) and `system-node-critical` (2000001000). Set `preemptionPolicy: Never` for a pod that should wait rather than displace others. **This is the mechanism that makes overprovisioning pause pods work** — give them priority `−1` and real workloads evict them instantly.
- **Real limits to quote**: kube-scheduler throughput is on the order of **~100 pods/second**; kubelet's default `--max-pods` is **110 per node** (and on EKS with the default VPC CNI, ENI/IP limits often bite first — an `m5.large` caps around 29 pods without prefix delegation); and Kubernetes' own large-cluster guidance is **no more than 5,000 nodes, 150,000 pods, 300,000 containers**.

### 5. Placement controls: affinity, topology spread, taints, PDB
- **`nodeSelector`** is the primitive: exact label match, AND-ed, hard. **`nodeAffinity`** is the expressive version, with `requiredDuringSchedulingIgnoredDuringExecution` (a hard filter — the pod stays Pending if unmet) and `preferredDuringSchedulingIgnoredDuringExecution` (a weighted score contribution, 1–100). Note `IgnoredDuringExecution` in every name: **these are checked once, at scheduling time.** Relabel a node and nothing moves.
- **Pod affinity/anti-affinity** places pods relative to *other pods* within a `topologyKey` domain. It is powerful and it is a documented scaling hazard: evaluating it requires, for each candidate node, examining pods across the whole domain, which is **effectively O(pods × nodes)** work. Kubernetes' own documentation advises against inter-pod affinity/anti-affinity in clusters larger than **several hundred nodes**. A `requiredDuringScheduling` anti-affinity with `topologyKey: kubernetes.io/hostname` on a 3,000-pod deployment can push per-pod scheduling latency into seconds and stall the whole queue.
- **`topologySpreadConstraints` is the modern replacement** and what you should reach for: declare `maxSkew` (the maximum allowed difference in matching-pod count between the fullest and emptiest domain), a `topologyKey` (`topology.kubernetes.io/zone`, `kubernetes.io/hostname`), and `whenUnsatisfiable: DoNotSchedule` (hard) or `ScheduleAnyway` (soft, a score contribution). `maxSkew: 1` across three zones on nine replicas gives you 3/3/3. Newer fields matter: `minDomains` (don't call it spread if only one zone is present), `matchLabelKeys` (include `pod-template-hash` so a rolling update's old and new pods are counted separately instead of blocking each other), and `nodeAffinityPolicy`/`nodeTaintsPolicy` for whether filtered-out nodes count as domains. It is cheaper than anti-affinity and expresses "spread, but don't get stuck" — which is what people actually want.
- **Taints and tolerations are the inverse**: a taint on a node *repels* pods unless they tolerate it (`NoSchedule`, `PreferNoSchedule`, `NoExecute` — the last one also evicts already-running pods). This is how you build dedicated pools: taint the GPU nodes `nvidia.com/gpu=true:NoSchedule`, taint the spot pool `spot=true:NoSchedule`, and only workloads that tolerate interruption go there. Pair it with a matching `nodeAffinity` — a toleration only grants *permission* to land there, it doesn't *attract* the pod.
- **PodDisruptionBudget is the guardrail on the whole system.** `minAvailable: 2` or `maxUnavailable: 1` is enforced by the API server's eviction subresource, so every *voluntary* disruption — `kubectl drain`, node upgrade, Cluster Autoscaler scale-down, Karpenter consolidation, VPA's updater — must ask permission and gets `429 Too Many Requests` when the budget is exhausted. It does **not** protect against involuntary events (kernel OOM, node hardware failure, spot reclamation past its 2-minute notice). The classic mistake: `minAvailable: 100%` or a PDB on a single-replica Deployment, which makes the budget permanently unsatisfiable and **blocks node drains forever** — cluster upgrades hang, and the autoscaler holds an empty node you keep paying for.

### 6. HPA v2: the control loop and the formula
- The HorizontalPodAutoscaler controller lives in kube-controller-manager and runs every **15 s** (`--horizontal-pod-autoscaler-sync-period`). Per cycle it reads the current metric, computes a desired replica count, and patches the target's `/scale` subresource.
- **Where metrics come from** — three distinct APIs: `metrics.k8s.io` (**metrics-server**, scraping each kubelet's Summary API roughly every 15 s; this is the *only* source for `type: Resource`), `custom.metrics.k8s.io` (an adapter such as **prometheus-adapter** or Zalando's **kube-metrics-adapter**, exposing per-object metrics like requests-per-second), and `external.metrics.k8s.io` (metrics not tied to a Kubernetes object — SQS queue depth, Kafka lag; this is the API KEDA implements).
- **The formula**, exactly: `desiredReplicas = ceil( currentReplicas × currentMetricValue / desiredMetricValue )`. For `type: Resource` with `averageUtilization`, `currentMetricValue` is **usage as a percentage of the pod's CPU *request*** — so **changing requests silently retunes your HPA.** Halve the request and every pod reports double the utilisation.
- **The 10% tolerance** (`--horizontal-pod-autoscaler-tolerance`, default `0.1`): if `|ratio − 1| ≤ 0.1` the controller does nothing. This is deliberate anti-flap damping, and it means a target of 70% really means "do nothing between 63% and 77%".
- **`behavior` is where production HPAs are actually tuned** (autoscaling/v2): `scaleDown.stabilizationWindowSeconds` defaults to **300 s** — the controller takes the *maximum* desired-replica recommendation over the trailing 5 minutes, so it scales down slowly and never on a dip. `scaleUp.stabilizationWindowSeconds` defaults to **0**, and the default scale-up policy is `max(4 pods, 100%) per 15 s` — so it can double every 15 seconds. **Asymmetry is correct**: scaling up early costs money, scaling down early costs an outage. Tighten `scaleUp` only if you have node headroom to absorb it.
- **Why averaged CPU is a bad proxy for queue-driven work**: for a worker pulling from SQS or Kafka, CPU is a *lagging* function of throughput, and if the queue backs up while workers are blocked on I/O, CPU can *fall* while the backlog grows — the HPA then scales *down* exactly when you need more consumers. The correct signal is **backlog per replica** (queue depth ÷ replicas, or consumer-group lag), which is what KEDA supplies. Averaging also hides skew: with an unbalanced load balancer, `avg` CPU of 50% can be one pod at 95% and nine at 45%.
- **The classic interaction bug**: HPA targets `cpu: 80%` of request, and the same pod has a CPU *limit* equal to its request. The app hits the limit, gets CFS-throttled, and its measured CPU **flatlines at the limit** — so the HPA sees 100% and scales, but each new pod is throttled too, so throughput per pod is capped and the HPA keeps adding replicas that can't help. You scale horizontally to work around a vertical stall. Remove or raise the CPU limit and the same load runs on half the replicas.

### 7. VPA: recommender, updater, admission controller — and why it fights HPA
- VPA is three separate components, and knowing which one does what is the whole answer:
  - **Recommender** — watches historical usage (from metrics-server, and it can bootstrap from Prometheus). It keeps **exponentially decaying histograms with a ~24-hour half-life** per container, and computes a target at roughly the **90th percentile** of observed usage plus a **~15% safety margin**, with `lowerBound`/`upperBound` bands for when action is warranted. Memory recommendations additionally account for observed OOM events by bumping the estimate.
  - **Updater** — compares running pods to the recommendation and, when a pod is outside the bounds, **evicts it** so it can be recreated with new resources. It respects PDBs and by default won't act on a workload with fewer than 2 replicas (`--min-replicas`). **This eviction is VPA's original sin**: to make your pod bigger, VPA kills it.
  - **Admission controller** — a mutating webhook that rewrites `resources` on every pod *create*, which is how the new values actually land. If the webhook is down, pods are created with their original requests and VPA silently does nothing.
- **`updateMode` is the dial**: `Off` (recommendations only — read them, apply them in Git; **this is the mode most mature teams actually run**), `Initial` (apply at creation, never evict), `Recreate`/`Auto` (evict to apply).
- **In-place resize is the fix.** `InPlacePodVerticalScaling` (KEP-1287) lets the kubelet update a running container's cgroup values through the pod's `/resize` subresource — alpha in **1.27**, **beta in 1.33**. Memory *decreases* may still require a restart (you can't take pages back from a process that's using them), and a container can declare a `resizePolicy` of `NotRequired` or `RestartContainer` per resource. This turns VPA from "a controller that kills your pods to help them" into something you can leave on.
- **The hard rule: VPA and HPA must not both drive the same resource.** The loop is vicious and precise: VPA lowers `requests.cpu` → HPA's metric is *usage ÷ request*, so utilisation percentage jumps → HPA adds replicas → load per pod falls → VPA lowers requests again → repeat. You get replica count and pod size oscillating together, and a bill that reflects the worst of both. The supported combination is **VPA on memory only + HPA on CPU or a custom metric**, expressed with `controlledResources: ["memory"]`. If you need both axes on the same signal, use HPA on a *custom* metric (RPS, queue depth) that isn't derived from requests at all.
- **Where VPA genuinely wins**: right-sizing the long tail. A platform team with 400 Deployments nobody has ever profiled gets more real money back from VPA-in-`Off`-mode recommendations, applied in Git, than from any amount of HPA tuning — because the *requests* are the bill.

### 8. The node and event layers: Cluster Autoscaler, Karpenter, KEDA — and the four-way conflict
- **Cluster Autoscaler (CA)** is *pod-driven, group-shaped*. Every 10 s it lists pods that are `Pending`/`Unschedulable` and, for each configured node group (ASG / MIG / VMSS), runs the **real scheduler predicates against a synthetic template node** for that group. If adding one would let the pod fit, it increments the group's desired capacity. Scale-down is the interesting half: a node is a candidate when its `Σ requests` is below `--scale-down-utilization-threshold` (**default 0.5**) *and* stays that way for `--scale-down-unneeded-time` (**default 10 min**) *and* every pod on it can be rescheduled elsewhere *and* no pod blocks it (no PDB violation, no local storage, no bare pod without a controller, no `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"`). Then it cordons and drains. **Because it reasons about requests, a cluster of over-requested pods will never look under-utilised and CA will never shrink it.**
- **Karpenter** is *pod-driven, instance-shaped*. Instead of picking from pre-declared node groups it reads the pending pods' actual requirements — requests, node selectors, tolerations, topology spread, architecture — and calls the cloud API for a right-sized instance from a broad `NodePool` of allowed instance types. Key behaviours to name: it **binds pods to the node it is about to create** (so the scheduler doesn't re-shuffle them), **consolidation** continuously replaces nodes with cheaper ones or deletes emptying ones (deleting empty nodes, and replacing an over-sized node with a smaller one), **drift** replaces nodes whose spec no longer matches the `NodePool`/`EC2NodeClass` (an AMI update becomes a rolling node replacement), and **disruption budgets** (`budgets: [{nodes: "10%"}]`, plus schedule windows) cap how much churn it may cause at once. The trade-off vs CA: Karpenter gets much better bin-packing and spot diversification, at the cost of far more node churn — every consolidation is a pod eviction, so **your PDBs and graceful shutdown had better be real.**
- **The scale-up latency chain — memorise this, it is the interview answer**: pod becomes `Pending` (0 s) → CA scan interval or Karpenter watch (0–10 s) → cloud provider API call, instance allocation (5–30 s; longer for scarce spot types) → **VM boot + kubelet registration** (30–60 s; a minimal OS like Bottlerocket is at the fast end) → node `Ready`, CNI ready → **image pull** (5 s cached, 30–180 s for a multi-GB image) → container start + readiness probe passing (5–60 s). **Total ~1–5 minutes, and it is dominated by boot and image pull, neither of which any autoscaler controls.**
- **Therefore: headroom is not optional.** The standard fix is **overprovisioning pause pods** — a Deployment of `pause` containers with real resource requests and a `PriorityClass` of `−1`. They occupy a node's worth of requests; when a real pod arrives, preemption evicts the pause pods *instantly* (they have no work to lose) and the real pod schedules onto already-warm capacity, while CA/Karpenter races to replace the reservation in the background. You are buying one node of latency insurance for the price of one node. Karpenter and Cluster Autoscaler both also support a static headroom/`--expander` configuration. Complementary fixes: pre-pull images with a DaemonSet, keep image size down, and set `terminationGracePeriodSeconds` honestly.
- **KEDA** attacks the signal problem. It implements the `external.metrics.k8s.io` API and ships **60+ scalers** (SQS, Kafka consumer lag, RabbitMQ, Redis list length, Prometheus query, Azure Service Bus, cron, HTTP RPS). A `ScaledObject` declares triggers; KEDA then *generates and manages an HPA* for the 1→N range and handles the **0↔1 transition itself** (the HPA API cannot scale to zero except behind an alpha gate). Default `pollingInterval` is 30 s and `cooldownPeriod` 300 s. **Scale-to-zero is the headline** — a nightly batch consumer costs nothing between runs — and `queue depth ÷ replicas` is the *right* signal for a worker precisely because it measures unserved demand rather than the CPU cost of serving it. A `cron` trigger that raises `minReplicaCount` at 08:50 is also the cleanest answer to the 3-minute node-boot problem for predictable diurnal load: **pre-scale on a schedule, react on a metric.**
- **The four as one system.** They are four controllers on four axes with no coordination layer between them, and the conflicts are structural: HPA↔VPA oscillate on CPU (§7); HPA scales in ~60 s while CA/Karpenter delivers nodes in ~3 min, so HPA's decision is *unfulfillable* for minutes; CA/Karpenter want to drain under-used nodes while PDBs forbid it, producing cordoned nodes you pay for indefinitely; and KEDA scaling from 0→200 replicas on a queue burst is simultaneously a node-scaling event, an image-pull storm, and a thundering herd against whatever database those 200 pods connect to (see [Backpressure & Throttling](../09_Message_Queues_Event_Streaming/Backpressure_Throttling.md)). **Design them as one control system: pick one scaler per axis, make sure their signals are independent, and set the slow layer's headroom to cover the fast layer's reaction time.**

## 5. Real-World Example
**The industry-wide overcommit gap (CAST AI, Datadog).** CAST AI's Kubernetes Cost Benchmark, computed over thousands of production clusters, has repeatedly reported average CPU utilisation around **10%** and memory around **20–23%** of provisioned capacity — meaning the median organisation buys roughly 4–10× the compute it uses. Datadog's Container Report independently finds that around **half of containers use less than a third of the CPU and memory they request**. Neither figure is about slow code; both are the direct output of requests being set by copy-paste and never revisited. The corollary is the most actionable cost lever in Kubernetes: **right-sizing requests is worth more than any code optimisation**, and VPA-in-recommendation-mode is how you find the numbers.

**CPU limits as a latency bug (Buffer, Indeed, and the Linux 5.4 fix).** Buffer's engineering team publicly documented chasing unexplained p99 latency spikes across their Kubernetes services and tracing them to CFS throttling from CPU limits set far below what multi-threaded runtimes needed; removing the CPU limits (while keeping requests) resolved the tail-latency problem. In parallel, engineers at Indeed diagnosed a genuine **kernel bug** in CFS bandwidth control — unused per-CPU quota slices expiring, so multi-threaded applications were throttled well before consuming their nominal quota — and the fix landed in **Linux 5.4** (`sched/fair: Fix low cpu usage with high throttling by removing expiration of cpu-local slices`) and was widely backported. The lesson to state in an interview: **check `container_cpu_cfs_throttled_seconds_total` and the node kernel version before you believe any story about your application's latency.**

**Past the documented ceiling (OpenAI, 7,500 nodes).** Kubernetes' own guidance caps a cluster at ~5,000 nodes and 150,000 pods. OpenAI published a detailed account of running clusters at **7,500 nodes** for large training jobs, and the interesting detail for a design discussion is *which* things broke: the API server and etcd (watch load, list requests, event volume), not the bin-packing — because their workloads are large pods that occupy whole nodes, so scheduling throughput and packing efficiency were comparatively easy. That inverts the usual pressure and makes the general point precisely: **your scaling bottleneck depends on pod shape.** Many small pods stress the scheduler and the 110-pods-per-node ceiling; few huge pods stress the control plane and the instance-type catalogue.

## 6. Code Example
A production-shaped Deployment: honest requests, **memory limit == request**, *no* CPU limit, spread across zones and nodes, with a PDB so the autoscaler and node upgrades can't take it out.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: checkout-api}
spec:
  replicas: 6
  selector: {matchLabels: {app: checkout-api}}
  template:
    metadata: {labels: {app: checkout-api}}
    spec:
      terminationGracePeriodSeconds: 45      # must exceed your longest in-flight request
      containers:
        - name: app
          image: registry.internal/checkout:1.42.0
          resources:
            requests:
              cpu: "600m"       # ← THE MOST IMPORTANT LINE: p95 steady-state usage, measured.
                                #   Drives scheduling AND is the denominator of the HPA's percentage.
              memory: "1Gi"
            limits:
              # NO cpu limit. Requests already set cpu.weight, so contention is shared fairly.
              # A cpu limit here would CFS-throttle a multi-threaded process in 25ms bursts
              # and destroy p99 while average CPU still reads "healthy". QoS becomes Burstable.
              memory: "1Gi"     # ← memory limit == request: memory is incompressible, so the
                                #   only safe overcommit ratio for it is 1.0.
          readinessProbe:                     # gates traffic; a slow probe extends scale-up time
            httpGet: {path: /readyz, port: 8080}
            periodSeconds: 5
            failureThreshold: 2
      # Spread first across zones, then across nodes. Cheaper and more forgiving than
      # requiredDuringScheduling pod anti-affinity, which is O(pods × nodes) and is not
      # recommended past a few hundred nodes.
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule    # hard: never let one AZ hold the majority
          minDomains: 3                       # "spread" is meaningless if only 1 zone is up
          matchLabelKeys: [pod-template-hash]  # count each ReplicaSet separately, or a rolling
                                               # update deadlocks against its own old pods
          labelSelector: {matchLabels: {app: checkout-api}}
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway   # soft: prefer node spread, but never go Pending for it
          labelSelector: {matchLabels: {app: checkout-api}}
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: checkout-api}
spec:
  minAvailable: 4          # of 6. NOT "100%" and NOT on a 1-replica Deployment — either makes the
                           # budget unsatisfiable and blocks node drains and CA scale-down FOREVER.
  selector: {matchLabels: {app: checkout-api}}
```

HPA v2 with explicit `behavior` and a request-rate custom metric, plus a KEDA `ScaledObject` for the worker where CPU is the wrong signal:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: checkout-api}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: checkout-api}
  minReplicas: 6           # floor = survive an AZ loss, not "cheapest steady state"
  maxReplicas: 60          # ceiling = protect the DB connection pool downstream
  metrics:
    - type: Resource                       # desired = ceil(cur × observed/target); observed is
      resource:                            # usage ÷ REQUEST, so retuning requests retunes this HPA
        name: cpu
        target: {type: Utilization, averageUtilization: 70}   # ±10% tolerance ⇒ inert 63–77%
    - type: Pods                           # via prometheus-adapter (custom.metrics.k8s.io):
      pods:                                # a LEADING signal — RPS moves before CPU does
        metric: {name: http_requests_per_second}
        target: {type: AverageValue, averageValue: "250"}
  behavior:                                # HPA picks the MAX desired across all metrics
    scaleUp:
      stabilizationWindowSeconds: 0        # default. React immediately on the way up…
      policies: [{type: Percent, value: 100, periodSeconds: 30},
                 {type: Pods,    value: 8,   periodSeconds: 30}]
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 600      # …but take the MAX recommendation over 10 min on the
                                           # way down. Default is 300s. Cheap insurance: shrinking
                                           # early costs an outage, shrinking late costs pennies.
      policies: [{type: Percent, value: 10, periodSeconds: 60}]   # ≤10% of fleet per minute
---
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: order-worker}
spec:
  scaleTargetRef: {name: order-worker}
  minReplicaCount: 0        # SCALE TO ZERO — KEDA owns 0↔1 itself; a plain HPA cannot do this
  maxReplicaCount: 200
  pollingInterval: 20
  cooldownPeriod: 300
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: https://sqs.us-east-1.amazonaws.com/1234/orders
        queueLength: "20"   # ← target BACKLOG PER REPLICA. This is the correct signal for a
                            #   worker: it measures unserved demand. CPU would FALL while the
                            #   queue grows if the workers are blocked on I/O, and the HPA
                            #   would then scale DOWN exactly when the backlog is exploding.
    - type: cron            # pre-scale for the known 09:00 spike, because a new NODE takes
      metadata:             # 1–5 minutes to arrive and no metric can predict that away
        timezone: Europe/London
        start: "50 8 * * 1-5"
        end: "0 19 * * 1-5"
        desiredReplicas: "12"
```

Finding the two failures nobody's dashboard shows by default:

```promql
# ── CFS THROTTLING: the fraction of 100ms periods in which the container was hard-stalled.
#    >1% on a latency-sensitive service is a real bug. >25% and you have a different app.
sum by (namespace, pod, container) (rate(container_cpu_cfs_throttled_periods_total{container!=""}[5m]))
  / sum by (namespace, pod, container) (rate(container_cpu_cfs_periods_total{container!=""}[5m]))

# ── THE OVERCOMMIT GAP: what you pay for vs what you use. This ratio IS the cost conversation.
sum(kube_pod_container_resource_requests{resource="cpu"}) / sum(kube_node_status_allocatable{resource="cpu"})
sum(rate(container_cpu_usage_seconds_total{container!=""}[5m])) / sum(kube_pod_container_resource_requests{resource="cpu"})

# ── OOMKILLS (not just restarts — restarts alone hide the cause)
increase(kube_pod_container_status_restarts_total[1h])
  and on(namespace,pod,container) kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1

# ── PODS THE SCHEDULER GAVE UP ON — this is the autoscaler's only trigger, so alert on duration
sum by (namespace) (kube_pod_status_unschedulable) > 0
# ── HPA PINNED AT ITS CEILING = the autoscaler is no longer autoscaling
kube_horizontalpodautoscaler_status_desired_replicas >= kube_horizontalpodautoscaler_spec_max_replicas
```

## 7. Design Variations & Alternatives

| Scaler | Axis it moves | Signal | Reaction time | Can go to zero? | Use when |
|---|---|---|---|---|---|
| **HPA** (autoscaling/v2) | replica **count** | avg CPU/mem % of *request*, or custom/external metric | ~30–90 s | No (alpha gate only) | Stateless request/response services with a metric that leads demand |
| **VPA** | pod **size** (requests) | decaying usage histogram, p90 + 15% | minutes–hours | n/a | Right-sizing the long tail; anything you've never profiled. Prefer `updateMode: Off` + Git |
| **In-place resize** (KEP-1287) | pod **size**, no restart | same as VPA | seconds | n/a | Kubernetes ≥1.33; makes VPA safe to leave on for stateful/singleton pods |
| **Cluster Autoscaler** | node **count**, fixed shapes | `Pending` pods; scale-down at <50% requests for 10 min | 1–5 min | Node groups to 0 | You have a small set of blessed instance types, or on-prem/VMSS/MIG |
| **Karpenter** | node **count + shape** | `Pending` pods' actual requirements; consolidation; drift | 1–3 min | Yes | AWS (and now others); you want bin-packing, spot diversity, and AMI drift handled |
| **KEDA** | replica count incl. **0** | queue depth, Kafka lag, cron, Prometheus, 60+ sources | ~30 s + pod start | **Yes** | Workers, batch, event consumers, spiky/idle workloads, scheduled pre-scaling |
| **Knative / serverless** | 0→N per request | concurrency per pod, request-driven | ms–seconds (with a queue proxy) | Yes | Request-per-container workloads that idle a lot; see [Serverless Computing](./Serverless_Computing_Lambda.md) |
| **Static + headroom** | nothing | a human and a spreadsheet | n/a | No | Fixed, predictable load; regulated environments; or as the *floor* under every scaler above |

**Cluster Autoscaler vs Karpenter, concretely.** CA's model is "someone already decided the instance shapes; I only turn the dial on each group." That is a virtue when your platform team wants a small, audited catalogue, when you're on-prem, or when you need CA's mature multi-cloud support. Its weaknesses: you must maintain one node group per (instance type × zone × taint set) combination, which explodes combinatorially and leads to teams over-provisioning shapes "just in case"; and it can only pack into shapes you predicted. Karpenter inverts it — you declare *constraints* (`karpenter.sh/capacity-type: [spot, on-demand]`, families, size floors) and it picks. You gain much tighter packing and real spot diversification; you pay in churn, because consolidation and drift are constantly replacing nodes, which means **PDBs, graceful shutdown, and `terminationGracePeriodSeconds` become load-bearing rather than decorative**. The middle path most teams land on: Karpenter for stateless/batch pools with aggressive consolidation and disruption budgets, plus one small static or CA-managed on-demand group for the control-plane-adjacent workloads (ingress controllers, Prometheus, stateful sets) that you don't want moving.

**Metric-source variations.** `type: Resource` (metrics-server) is free and universally available but only exposes CPU/memory as a fraction of request. `prometheus-adapter` turns any PromQL into a custom metric — the most flexible option and the one that lets you scale on `p99 latency` or `active connections`, at the cost of putting Prometheus in the critical path of your autoscaler. **KEDA is usually the better answer than a hand-rolled adapter** because the scalers are already written and it handles scale-to-zero. And a `cron` trigger is not a cop-out: for predictable diurnal load, **scheduled pre-scaling beats any reactive loop**, because no reactive loop can beat a 3-minute node boot.

## 8. Pros and Cons

### Requests + limits as the resource model
- **Pros**: fully declarative and deterministic — the same pod schedules the same way regardless of momentary load; a single number (`requests`) simultaneously drives scheduling, cgroup weight, eviction ranking, and the HPA denominator; and it makes capacity a *reviewable artifact in Git* rather than an emergent property.
- **Cons**: it demands a number humans cannot estimate, so in practice requests are set 3–5× too high and the cluster runs at ~10–20% utilisation (CAST AI's measured average); the same field means two different things (schedule-time promise, run-time weight), which is a permanent source of confusion; and CPU limits — the natural-looking safety mechanism — actively harm latency via CFS throttling.

### CPU limits: set them or don't
- **Pros of setting them**: hard, predictable cost attribution; protection of co-tenants from a pod that would otherwise consume all idle CPU; `requests == limits` unlocks `Guaranteed` QoS, last-to-be-evicted status, and exclusive CPU pinning with the static CPU manager; and required for untrusted or multi-tenant workloads where a neighbour is an adversary.
- **Cons of setting them**: CFS throttling stalls *every* thread in the cgroup for the remainder of a 100 ms period, adding up to 75 ms of pure queueing to p99 while average CPU looks perfectly normal; multi-threaded runtimes need limits far above their average to avoid it; it distorts the very CPU metric your HPA scales on; and it wastes the idle CPU on the node that the pod could have used for free.

### The multi-autoscaler stack
- **Pros**: each axis is genuinely necessary — replicas for concurrency, pod size for right-sizing, nodes for capacity, events for idle/spiky work — and together they turn a fixed-cost fleet into something that tracks demand within minutes, with scale-to-zero making idle workloads literally free.
- **Cons**: four uncoordinated control loops on four different clocks, with two documented conflicts (HPA↔VPA on CPU, PDB↔scale-down) and one structural gap (HPA reacts in 60 s, nodes arrive in 3 min) that you must pay for with idle headroom; every additional controller is another CRD, another webhook, and another thing that fails silently and leaves you at `minReplicas` during a spike.

## 9. Failure Scenarios & What Can Go Wrong
- **SYMPTOM**: p99 latency spikes to 100–200 ms in bursts, but average CPU utilisation is a calm 60–100% and there's no GC pressure or slow query. **ROOT CAUSE**: CFS throttling — the container exhausts its 100 ms CPU quota early because it has more runnable threads than its `limits.cpu`, and every thread is dequeued for the rest of the period. **FIX**: graph `rate(container_cpu_cfs_throttled_periods_total[5m]) / rate(container_cpu_cfs_periods_total[5m])`; remove the CPU limit on latency-sensitive services (keep the request), or raise it to ≥ the runtime's real parallelism; check the node kernel is ≥5.4; and cap the runtime's thread count (`GOMAXPROCS`, JVM `ActiveProcessorCount`) to match the limit if you must keep one.
- **SYMPTOM**: Pods die with `exitCode: 137` / `reason: OOMKilled` and enter `CrashLoopBackOff`; no application error is logged. **ROOT CAUSE**: the container's memory cgroup hit `limits.memory` and the kernel `SIGKILL`ed it — there is no grace period, so nothing gets logged on the way out. **FIX**: set `requests.memory == limits.memory` (no memory overcommit), size the limit from the observed peak plus headroom (VPA's memory recommendation is good at this), and make sure runtime heap settings derive from the cgroup limit (`-XX:MaxRAMPercentage=75`, `GOMEMLIMIT`) rather than the node's total RAM.
- **SYMPTOM**: The cluster reports 95% CPU allocated and refuses to schedule, but node dashboards show 20% actual utilisation — and Cluster Autoscaler keeps adding nodes. **ROOT CAUSE**: requests are 3–5× real usage; the scheduler sums requests only, so the cluster is "full" of reservations nobody uses. **FIX**: run VPA in `updateMode: Off` and apply its recommendations in Git; alert on the `requests ÷ usage` ratio per namespace; enforce a `LimitRange` default and a `ResourceQuota` ceiling per namespace so nobody can quietly reserve a node.
- **SYMPTOM**: A node drain or cluster upgrade hangs for hours; a cordoned, empty node stays in the cluster and on the bill. **ROOT CAUSE**: an unsatisfiable PodDisruptionBudget — `minAvailable: 100%`, or a PDB on a 1-replica Deployment, or `maxUnavailable: 0` — so every eviction request returns `429` forever. **FIX**: PDBs must always leave slack (`minAvailable: N−1` at minimum, and never a PDB on a singleton); alert on `kube_poddisruptionbudget_status_desired_healthy >= kube_poddisruptionbudget_status_expected_pods` and on nodes cordoned longer than an hour.
- **SYMPTOM**: Replica count and pod size oscillate together in a sawtooth; the bill goes up and nothing gets faster. **ROOT CAUSE**: HPA and VPA both driving CPU. VPA cuts `requests.cpu`, which inflates the HPA's usage-over-request percentage, which adds replicas, which lowers per-pod usage, which makes VPA cut again. **FIX**: one controller per resource — `controlledResources: ["memory"]` on the VPA and CPU (or a custom metric) on the HPA. Never both on CPU.
- **SYMPTOM**: HPA scales from 10 to 40 replicas in 30 seconds, but 30 pods sit `Pending` for three minutes while users get 503s. **ROOT CAUSE**: the scale-up latency chain — cloud API + VM boot + kubelet ready + image pull is 1–5 minutes and no autoscaler can shorten it. **FIX**: overprovisioning pause pods at `PriorityClass: −1` so a node's worth of warm capacity is always available; pre-pull images via a DaemonSet and shrink the image; add a KEDA `cron` trigger for known daily peaks; and raise `minReplicas` to cover the burst you can't predict.
- **SYMPTOM**: Scheduling latency climbs to seconds per pod and a large Deployment takes many minutes to roll out. **ROOT CAUSE**: `requiredDuringSchedulingIgnoredDuringExecution` pod anti-affinity on a large workload — its evaluation is effectively O(pods × nodes) and Kubernetes explicitly warns against it past a few hundred nodes. **FIX**: replace it with `topologySpreadConstraints` (`maxSkew: 1`, `whenUnsatisfiable: ScheduleAnyway` for the node dimension), keeping a hard constraint only on the zone dimension where it's genuinely required.
- **SYMPTOM**: All three replicas of a service become unavailable at once during a routine node event; the Deployment looked correctly spread in `kubectl get pods`. **ROOT CAUSE**: nothing enforced spread — the bin-packing scorer legitimately placed all three on one node, or `topologySpreadConstraints` was set with `whenUnsatisfiable: ScheduleAnyway` and quietly ignored, or a rolling update's new pods weren't counted separately so spread silently degraded. **FIX**: hard zone spread plus soft host spread, `matchLabelKeys: [pod-template-hash]`, and verify with `kubectl get pods -o wide` in CI — then a PDB as the second line of defence.
- **SYMPTOM**: The HPA sits at `maxReplicas` while latency stays bad, or reports `<unknown>` for its metric and never acts. **ROOT CAUSE**: either the real bottleneck is downstream (a saturated database connection pool that more replicas make *worse*), or metrics-server / prometheus-adapter is down and the HPA has no signal — in which case it holds the last replica count silently. **FIX**: alert on `desired >= max` and on the HPA's `ScalingActive` condition being false; treat `maxReplicas` as a deliberate protection for downstream dependencies and document what it protects.

## 10. Impact on Scalability, Reliability & Cost
- **Scalability**: the ceilings are arithmetic and worth reciting. Per node: `min(--max-pods (default 110), allocatable ÷ request)` — a `m5.2xlarge` (8 vCPU) with ~7.91 vCPU allocatable holds `floor(7910/500) = 15` pods requesting `500m`, so the pod ceiling never binds; flip to pods requesting `50m` and you hit 110 first and strand 2.4 vCPU. Per cluster: ~5,000 nodes / 150,000 pods, with kube-scheduler at ~100 pods/s (a 10,000-pod rollout is ~100 s of pure scheduling before any container starts) and `percentageOfNodesToScore` dropping to a 5% floor at 5,000 nodes, which trades placement quality for that throughput. **The number that actually limits you first is usually your requests, not any of these limits.**
- **Reliability**: the composition is multiplicative and cheap to reason about. Hard zone spread across 3 AZs means losing one AZ costs `⌈1/3⌉` of capacity, so `minReplicas` must be ≥ `1.5 ×` steady-state to absorb it. A PDB of `minAvailable: 4` of 6 means any voluntary disruption removes at most 33% at a time. `requests.memory == limits.memory` removes the entire OOMKill class. And the honest reliability arithmetic for autoscaling: if scale-up takes 3 minutes and your traffic can triple in 30 seconds, **the autoscaler cannot save you** — only headroom, load shedding ([Load Shedding & Graceful Degradation](../07_Load_Balancing_Scalability/Load_Shedding_Graceful_Degradation.md)), or scheduled pre-scaling can.
- **Cost**: you pay for `Σ allocatable`, you use `Σ actual`, and the scheduler bills you for `Σ requests`. Concretely: 400 pods each requesting `1000m` but using `250m` need `400 × 1000m ÷ 7910m ≈ 51` nodes, where actual usage needs `400 × 250m ÷ 7910m ≈ 13`. At roughly **$0.384/hr** for an on-demand `m5.2xlarge` in `us-east-1`, that's **~$14,100/month vs ~$3,600/month — about $10,500/month for one wrong number in a YAML file.** Right-sizing requests, then Karpenter consolidation to pack them tightly, then spot for the interruptible fraction, is the correct order of operations — right-size first, because bin-packing waste is just multiplied by the price of whatever you bin-pack onto. See [Cost Estimation & FinOps](../01_Planning_Foundations/Cost_Estimation_FinOps.md).

## 11. When NOT to Use This
- **Don't set CPU limits on latency-sensitive online services.** CFS throttling adds up to 75 ms of dead time per 100 ms period to a multi-threaded process, and the request alone already gives you proportional-share protection. Set limits for batch, for untrusted tenants, or when you need `Guaranteed` QoS and CPU pinning — and know you're trading tail latency for predictability.
- **Don't put an HPA on a workload whose bottleneck is downstream.** If the constraint is a 100-connection Postgres pool or a rate-limited third-party API, adding replicas increases contention and error rate. The right tool is a queue, a connection proxy (PgBouncer), or load shedding — not more pods.
- **Don't use VPA in `Auto`/`Recreate` mode on singletons or stateful workloads** on a cluster without in-place resize. The updater applies recommendations by *evicting the pod*; for a single-replica leader or a stateful primary that's a self-inflicted failover on a schedule you don't control. Use `updateMode: Off` and apply in Git, or wait for `InPlacePodVerticalScaling` (beta in 1.33).
- **Don't scale on averaged CPU for queue-driven workers.** CPU is a lagging, I/O-distorted proxy for demand, and it can *fall* while the backlog grows — so the HPA scales down at exactly the wrong moment. Use backlog-per-replica via KEDA.
- **Don't use `requiredDuringScheduling` pod anti-affinity in a large cluster.** Its evaluation cost is effectively O(pods × nodes) and Kubernetes' own docs advise against it beyond a few hundred nodes. `topologySpreadConstraints` expresses the same intent at a fraction of the scheduling cost.

## 12. Interview Perspective
- **What interviewers expect**: the distinction, stated cleanly and unprompted. Say: **"Requests drive scheduling — the scheduler only ever sums requests and never looks at actual usage — and limits drive runtime enforcement in the cgroup. That's why a cluster can be 100% allocated at 20% utilised."** Then immediately add the asymmetry: **"CPU is compressible so a limit throttles you; memory is not, so a limit kills you at exit 137."** Those two sentences cover most of what a Staff+ interviewer is checking for.
- **The trap question**: *"Your p99 latency is terrible but CPU utilisation is only 60%. What's wrong?"* The wrong answer immediately adds replicas or blames GC/the database. The right answer: "60% of *what* — of the request or of the node? If the pod has a CPU limit, average CPU can look fine while the container is being CFS-throttled in 75 ms chunks, because averaging over a 15-second scrape hides a stall that recurs every 100 ms. I'd check `container_cpu_cfs_throttled_periods_total` over `container_cpu_cfs_periods_total` first; if that's non-zero, the fix is removing or raising the CPU limit, not adding pods — and adding pods via HPA would actively mislead me because the HPA's metric is distorted by the same throttling."
- **The math question**: *"200 pods, `requests.cpu: 500m` each, on `m5.2xlarge`. How many nodes, and what would you change?"* Walk it: `m5.2xlarge` = 8 vCPU, allocatable ≈ **7,910m** after kube-reserved (~90m) and system-reserved. `floor(7910 ÷ 500) = 15` pods/node by CPU — well under the 110-pod ceiling, so CPU binds. `⌈200 ÷ 15⌉ = 14` nodes. Then add reality: `maxSkew: 1` across 3 AZs and a PDB mean you need N+1 for drains, so **15 nodes ≈ $0.384/hr × 15 × 730 ≈ $4,200/month**. Then the punchline: "if actual usage is `150m` — which the industry average of ~10% utilisation suggests — the honest request is `200m`, that's 39 pods/node, `⌈200/39⌉ = 6` nodes, **~$1,700/month**. So my first action is measuring usage, not tuning the autoscaler."
- **The subtle "why" question**: *"Why doesn't the scheduler just schedule on actual usage?"* Because scheduling must be **deterministic and idempotent**. Usage-based placement would make the same pod land differently depending on the second it was submitted, would oscillate as usage fluctuates, and would let a pod that happens to be idle at bind time get scheduled onto a node it will then crush — you cannot un-schedule it, since the scheduler has no eviction authority. Kubernetes deliberately pushes usage-awareness into *second* loops that run after the fact: kubelet eviction, the descheduler's `LowNodeUtilization`, VPA, and Karpenter consolidation. **Declared capacity for the decision, observed usage for the correction.**
- **Bonus signals**: naming which of the four autoscalers you mean and that HPA+VPA on CPU oscillate; `oom_score_adj` values per QoS class and that a bigger memory request literally buys survival; overprovisioning pause pods at negative `PriorityClass` as the answer to node-boot latency; `matchLabelKeys: [pod-template-hash]` so topology spread doesn't deadlock a rolling update; that bind is optimistic and kubelet admission can still reject with `OutOfcpu`; `percentageOfNodesToScore` as an explicit optimality-for-throughput trade; Karpenter drift turning an AMI bump into a rolling node replacement; and KEDA `cron` as the honest answer to predictable load because no reactive loop beats a 3-minute boot.

## 15. Summary (TL;DR)
**Requests and limits share a YAML block and nothing else: a request is a promise to the *scheduler*, which does nothing but sum requests against a node's allocatable capacity and never once looks at real usage, while a limit is a threat from the *kernel*, enforced continuously by cgroups.** That single split explains the defining Kubernetes number — clusters that report 95% allocated at 10–20% utilised (CAST AI's measured average across thousands of clusters), which is the largest controllable line item in most cloud bills. The enforcement asymmetry is the second thing to internalise: **CPU is compressible, so `limits.cpu: 1` becomes a 100 ms CFS quota that a 4-thread process burns in 25 ms and is then hard-stalled for 75 ms — average CPU reads "healthy" while p99 is destroyed, which is why `container_cpu_cfs_throttled_seconds_total` is the first metric to check on any unexplained tail latency, and why a serious industry position says to set CPU requests and no CPU limits. Memory is not compressible, so exceeding `limits.memory` is an instant kernel `SIGKILL`, exit 137, no grace period — therefore always set `requests.memory == limits.memory`.** Those two fields also *derive* your QoS class (`Guaranteed` when requests == limits everywhere, `oom_score_adj −997`, evicted last, eligible for exclusive CPU pinning; `Burstable` in between, where a larger memory request literally buys a better survival score; `BestEffort` with nothing set, `oom_score_adj 1000`, evicted first), which fixes both the eviction order under node pressure and who the kernel picks. The scheduler itself is a two-phase loop — **filter** on predicates (resources fit, affinity, taints, volume topology, host ports) then **score** with weighted priorities (`LeastAllocated` to spread or `MostAllocated` to bin-pack, image locality, spread) then **optimistically bind**, with kubelet admission still able to reject as `OutOfcpu`, and `PriorityClass` preemption able to displace lower-priority pods — running at roughly 100 pods/s against ceilings of 110 pods/node, ~5,000 nodes and ~150,000 pods. Control placement with `nodeAffinity` for hard/soft node choice, **`topologySpreadConstraints` (`maxSkew`, `whenUnsatisfiable`, `matchLabelKeys: [pod-template-hash]`) rather than `requiredDuringScheduling` pod anti-affinity**, which is effectively O(pods × nodes) and unsafe past a few hundred nodes, plus taints/tolerations for dedicated and spot pools and a **PodDisruptionBudget that leaves real slack** — because every voluntary eviction, including autoscaler scale-down and node upgrades, must ask its permission, and an unsatisfiable PDB blocks drains forever. Then there are **four** autoscalers on four axes: HPA moves replica count on a 15 s loop with `desiredReplicas = ceil(currentReplicas × current/target)`, a 10% tolerance, a 300 s scale-down stabilisation window and 0 s on the way up; VPA moves pod size from a decaying usage histogram (p90 + ~15%) via a recommender, an updater that *evicts pods to apply* (until `InPlacePodVerticalScaling`, beta in 1.33), and a mutating admission webhook; Cluster Autoscaler and Karpenter move node count off `Pending` pods, with CA turning fixed node-group dials and scaling down nodes under 50% requests for 10 minutes, and Karpenter instead choosing instance types directly with consolidation, drift, and disruption budgets; and KEDA scales on events — queue depth, Kafka lag, cron — with the unique ability to reach zero, which matters because **backlog-per-replica is the right signal for a worker where averaged CPU can fall while the queue grows and make the HPA scale down at the worst moment.** They do not coordinate, so **never let HPA and VPA both drive CPU** (VPA cuts requests → utilisation percentage rises → HPA adds pods → VPA cuts again: use VPA on memory only), and remember the scale-up latency chain — Pending → autoscaler decision → cloud API → VM boot → kubelet ready → image pull → readiness — is **1–5 minutes**, which no configuration removes. **So right-size requests first, drop CPU limits and pin memory limits to requests, spread with topology constraints behind a real PDB, pick exactly one scaler per axis, and buy the missing minutes with overprovisioning pause pods at a negative PriorityClass or a scheduled pre-scale — because the autoscaler you cannot make faster is the node.**
